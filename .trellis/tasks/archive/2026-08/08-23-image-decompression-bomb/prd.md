# 修复图片上传解压炸弹 DOS

## Goal

阻止普通账号通过小压缩体积、高像素尺寸或超多帧图片耗尽 JVM 的 CPU 与堆内存，同时限制 Base64 请求体和并发图片处理量，保障图片上传期间其他用户仍可正常使用服务。

## Background

- 安全问题：SEC-10，CWE-409 / CWE-400，中危，高置信度。
- `model/src/main/java/com/ayor/entity/Base64Upload.java:8-15` 当前没有 Base64 文本长度约束。
- `common/src/main/java/com/ayor/image/ImageProcessor.java:42-44,67-73,101-106,247-268` 当前在完整 Base64 解码后才检查 10 MiB，并在校验宽、高、总像素或帧数上限前调用 `ImageReader.read(0)`。
- 用户端主题、评论、贴纸、头像、横幅、话题封面与管理端装饰资源均可进入共享图片处理链路；管理端 `TopicServiceImpl` 仍有一条直接调用 `MinioService#uploadBase64` 的旁路。
- 两个 Web 应用当前都没有通用 JSON 请求体大小限制；Tomcat 的 `maxPostSize` 只约束表单参数解析，不是 JSON 请求体通用上限。

## Requirements

### R0：确认的安全上限

- Base64 解码后单图最多 10 MiB；含 data URL 头部的 Base64 文本上限按该字节边界计算。
- 任一图片或动画帧的宽、高分别最多 8192 px，单帧总像素最多 16,777,216。
- 正文动图最多 50 帧；贴纸仍只允许 1 帧。
- 单个 HTTP 请求体最多 16 MiB。
- 每个 JVM 同时最多处理 2 张图片，槽位用尽时快速失败。

### R1：Base64 与请求体边界

- 在 Base64 解码分配字节数组前，根据编码文本长度拒绝不可能落在 10 MiB 解码后上限内的输入。
- `Base64Upload.base64` 增加可验证的文本长度约束；所有直接或嵌套接收该模型的上传入口必须启用级联校验。
- 用户端与管理端对请求体实施相同的字节上限；既拒绝已声明超限的 `Content-Length`，也在无长度或分块传输读取超过上限时终止。
- 超限请求不得进入图片解码、对象存储或数据库副作用。

### R2：完整解码前元数据预检

- 使用 `ImageReader` 先取得首帧宽、高和帧信息，再调用 `read(0)`。
- 宽、高、`width × height` 或帧数任一超过上限时立即拒绝；像素乘法必须使用 `long`，避免整数溢出绕过。
- 表情图片继续拒绝多帧；正文图片继续允许 GIF，但必须受统一帧数上限约束。
- 上传声明的扩展名不得成为绕过真实图片格式识别与限制的手段。

### R3：并发处理边界

- 每个 JVM 的元数据解析、完整解码、缩放和转码共享同一个并发上限。
- 并发槽已满时快速失败，不允许无界排队继续堆积请求体和解码任务。
- 无论成功或异常都必须释放并发槽。

### R4：消除上传旁路

- 所有会接收新 Base64 图片的生产路径必须经过同一套 `ImageProcessor` 防护。
- 已有平台图片 URL 的保留/复用行为不应被误当作新 Base64 数据解码。
- 不改变现有 jpg/jpeg/png/webp/gif 的业务格式规则、对象路径与成功响应结构，除非安全上限要求拒绝。

### R5：可观测拒绝行为

- 图片尺寸、像素、帧数或 Base64 超限返回明确且不泄露内部实现的客户端错误。
- 请求体超限返回 HTTP 413；并发已满返回 HTTP 429；响应继续使用统一 `Result<T>` 结构，不得落为未知 500 错误。

## Acceptance Criteria

- [x] AC1：受控的“小体积、超大尺寸”合法图片在 `ImageReader.read(0)` 前被拒绝，测试过程不分配对应大图栅格。
- [x] AC2：边界内图片仍可按现有贴纸/正文规则处理；超宽、超高、超总像素分别被拒绝。
- [x] AC3：静态贴纸通过，多帧贴纸被拒绝；正文 GIF 在帧数上限内通过，超过上限被拒绝。
- [x] AC4：Base64 文本在解码前被长度门禁拒绝，解码后的 10 MiB 上限继续保留作为第二道防线。
- [x] AC5：声明超限与分块读取超限的请求体都在业务副作用前收到 HTTP 413。
- [x] AC6：并发处理达到上限后新任务快速失败；已有任务结束或抛错后槽位可再次取得。
- [x] AC7：全仓搜索不存在新 Base64 图片绕过共享防护直接上传的生产调用点。
- [x] AC8：`common`、`model`、`web-app`、`web-admin` 的受影响测试通过，并执行 `git diff --check`。
- [x] AC9：使用受控攻击样本运行时，拒绝前后堆内存不出现与声明像素规模对应的增长；记录验证方式与观察结果。

## Out of Scope

- 不改为 multipart 或直传对象存储协议。
- 不对历史已存储图片做离线扫描、重编码或迁移。
- 不引入外部图像沙箱进程、容器级配额或分布式全局并发控制。
- 不修改反向代理/CDN 的请求体上限；部署层应另行配置为不高于应用上限。

## Key Decisions

- 用户已确认采用推荐安全档；安全边界优先于 48 MP 手机原图和“单请求 7 张接近 10 MiB 图片”的极端兼容性。
- 请求体限制覆盖两个 Web 应用的所有 POST/PUT/PATCH 请求，避免依赖易遗漏的上传路由白名单。
- 并发限制按 JVM 生效；当前任务不引入 Redis 或数据库协调。
