# 技术设计：帖子最多 7 张图片并完整返回

## 边界与职责

- `TipTapUtils` 继续作为 TipTap JSON 的单一解析入口，提供图片计数/校验所需的公共能力，并保留 `extractAllImageUrls(...)` 作为完整 URL 投影。
- `ThreaddServiceImpl` 在创建和编辑流程进入 Base64 转换前执行业务限制校验，确保失败时没有上传或持久化副作用。
- threads 列表转换和收藏列表转换改用完整图片 URL 提取，不在返回层设置数量上限。

## 数据流

1. Controller 通过 `@Valid ThreadDTO` 接收正文。
2. Service 解析 TipTap JSON 并校验 `image` 节点数量不超过 7。
3. 校验通过后，沿用现有 Base64 图片转换、帖子保存、图片引用同步和消息/缓存/索引流程。
4. 列表读取时从已保存的 TipTap 正文按文档顺序提取全部非空图片 URL 到 `ThreadVO.imageUrls`。

## 关键决策

- 限制的是正文中的图片节点总数，不只是本次 Base64 上传数量；这能防止 URL 输入绕过业务规则。
- 返回层不复用“7 张上限”进行裁剪。写入规则保证新内容最多 7 张，而完整提取可正确兼容历史数据。
- 不新增 DTO 字段或数据库字段，避免冗余计数状态和迁移成本。
- 继续使用当前 Service 返回错误字符串、Controller `Result.messageHandler(...)` 的错误响应模式。

## 兼容与回滚

- 无数据库迁移，旧数据保持不变。
- 回滚只需恢复工具方法调用和 Service 校验；不会产生不可逆数据变更。
- 历史超限帖子可读但不可原样再次保存，符合“最终正文必须降至 7 张以内”的规则。
