# Service 文档设计

## 交付边界

本任务只新增 `review/` 下的 Markdown 文档，不修改 Java 业务代码、配置或测试。接口和实现作为同一个逻辑服务说明，模块间同名类分别记录。

## 文档结构

```text
review/
├── README.md                 # 范围、统计口径、模块导航和整体协作关系
├── web-app-services.md       # 用户端 44 个常规 service + 2 个包外 Spring 服务
├── web-admin-services.md     # 管理端 29 个常规 service + 1 个包外 Spring 服务
└── common-services.md        # 2 个公共存储/图片服务
```

采用按模块拆分而非“一服务一文件”，原因是 78 个独立文件会制造目录噪音和维护负担；四份文档既能控制单文件体量，也能保留明确模块边界。

## 条目契约

每个服务使用三级标题，标题包含唯一稳定标识：

```markdown
### `web-app:AccountService`
```

每个条目至少包含：

- **作用**：一句话说明该服务解决的问题；
- **主要职责**：基于公开方法和实现分支概括能力；
- **关键协作/数据边界**：说明主要 Mapper、其他服务、Redis、MQ、WebSocket、Elasticsearch 或对象存储；
- **代码入口**：链接接口和实现；没有接口时链接实现类；
- **主要入口方法**：列代表性公开方法，不追求逐方法 API 手册。

对于仅继承 `IService` 且没有自定义方法的接口，明确标注“当前未定义额外业务入口”，不从类名推测功能。

## 总览内容

`review/README.md` 记录：

- 78 个条目的统计口径和模块分布；
- 接口/实现合并、跨模块同名服务、包外 `@Service` 的处理规则；
- 用户端、管理端、公共能力之间的高层关系；
- 三份模块文档的导航；
- 文档基于当前代码快照，后续新增 service 时需同步维护。

## 可追溯性与覆盖校验

- 以“模块 + 类名”作为唯一 ID，例如 `web-app:PostService`、`web-admin:PostService`。
- 从源码重新生成期望 ID：两个模块 service 目录的顶层抽象、两个 common 服务、三个包外 `@Service`。
- 从 Markdown 三级标题提取实际 ID，比较集合差异、重复项和总数。
- 验证四份文档内的相对源码链接均指向存在的文件。

## 兼容性与回滚

- 仅新增文档，对运行时无兼容性、迁移或部署影响。
- 若结构不符合预期，可独立删除 `review/` 新增文件回滚，不影响业务代码。
